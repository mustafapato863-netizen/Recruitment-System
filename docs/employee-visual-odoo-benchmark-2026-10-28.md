# وضوح رحلة الموظف ومقارنتها بـ Odoo — 28 أكتوبر 2026

هذا ملحق لـ [مراجعة رحلة الموظف](employee-journey-audit-2026-10-28.md). أكد المستخدم ترتيب المراجع: Odoo للتدفق، وLinear لـ My Work والكثافة، وAshby للـPipeline، وNotion للكروت والحالات الفارغة. لوحات SGH في `docs/recruitment-visual-reference-complete/` مرجع بصري وتصوري، وليست دليلًا على أن الميزات المعروضة فيها تعمل أو موجودة في هذه المنتجات.

المقارنة تشير إلى تجربة الموظف في النسخة المحلية فوق `fc3cce2` مع التعديلات المحلية. نتائج المشروع تأتي من مراجعة المصدر وجولة المتصفح الموثقة في التقرير السابق؛ لم يُعد تنفيذ كل إجراء، ولم تُختبر كل الأدوار أو التكاملات.

### فجوات إضافية تقترحها المقارنة

| الفكرة | حالة RecruitFlow التي تم التحقق منها | المقترح |
| --- | --- | --- |
| قائمة أولويات مركزة مثل Linear | توجد فلاتر Overdue/Today/Waiting مع تكرار الأعداد في ملخص أعلى الصفحة. إجراء إكمال المهمة المستقلة غير مكتمل حسب المصدر | دمج التمييز البصري مع صف مدمج قابل للتنفيذ؛ لا نتعامل مع الكثافة كتصغير خط أو إخفاء معلومة ضرورية |
| حالة المرشح في Ashby | بطاقات الـPipeline الحالية تعرض المرحلة، وأحيانًا سبب توقف وزر الفرز؛ قائمة المرشحين تخلط آخر نشاط مع Next action | تمييز `يحتاج فعلي` و`بانتظار آخرين` و`مكتمل` بنص وأيقونة ولون، من بيانات موثوقة. لا ننسخ حدود أيام Ashby أو نعتبرها SLA للمشروع قبل تعريفها |
| التنقل السريع بين مرشحي نفس القائمة | Ashby يوثق السابق/التالي والإغلاق والعودة. في v2 اختُبرت العودة مع فلتر Candidates؛ لم يُثبت وجود السابق/التالي في ملف v2 | اقتراح السابق/التالي ضمن المرشحين الذين تشملهم القائمة والصلاحيات فقط؛ إبقاء الفلتر، والتحذير من الخروج مع تغييرات غير محفوظة. يتطلب اختبارًا وتصميمًا قبل التنفيذ |
| عرض Pipeline كقائمة أو بطاقات | Ashby يوثق list/card لبعض تقارير الـPipeline؛ v2 يعرض لوحة مراحل، وOpen jobs فقط لديه Cards/List | إضافة عرض قائمة للمرشحين في نفس الوظيفة عند الحاجة، مع نفس المرحـلة والصلاحيات والإجراءات؛ لا يفترض البحث الحالي في Candidates أنه بديل متطابق |
| المراجعة المجمعة | Ashby يوثق مراجعة المتقدمين ومجموعة أفعال؛ مقارنة v2 موجودة لمرشحين محددين | دراسة مراجعة متتابعة للـCV والخطوة التالية أولًا. أي نقل أو رفض جماعي قرار لاحق يتطلب تحقق صلاحيات، تأكيد واضح ونتيجة لكل سجل؛ لم نثبت توفره في v2 |
| حالة فارغة قابلة للتصرف | توجد حالات فارغة في الشاشات الحالية | نص يوضح «لا نتائج بسبب الفلتر» مقابل «لا توجد سجلات بعد»، مع زر مسح الفلتر أو بدء الإضافة حيث تسمح الصلاحية؛ الاقتراح مستلهم من طلب المستخدم لا من سلوك موثق في Notion |

لا يلزم تطبيق كل خصائص تلك المنتجات: الأولوية لرحلة الموظف والقدرات الموجودة وتكاملها، ثم تحسينات السرعة التي أثبت الاختبار أنها مطلوبة.

## ما يحتاجه التصميم ليوجه الموظف

المطلوب أن يميز المستخدم بسرعة بين **ما يحتاج فعله، وما ينتظر شخصًا آخر، وما انتهى، وما يحتاج تصحيحًا**. تستخدم الألوان والأيقونات لتأكيد المعنى، ويظل اسم الحالة والفعل ظاهرين؛ لا تعتمد حالة مهمة على اللون وحده.

| العنصر | الاتجاه المقترح | مثال عملي |
| --- | --- | --- |
| الإجراء الأساسي | زر واضح واحد حسب الحالة والصلاحية، به أيقونة ونص | «تسجيل الفرز»، ثم «جدولة المقابلة» عند اكتمال المتطلبات |
| الحالات | ألوان دلالية من tokens المشروع مع نص؛ الأحمر للتأخير أو الخطأ، الكهرماني لما يحتاج انتباهًا، الأخضر للمكتمل، والأزرق للمعلومات أو الإجراء | `متأخر · متابعة المرشح`، `بانتظار تقييم المقابل` |
| التسلسل البصري | عنوان واضح، نص أساسي داكن كافٍ للقراءة، بيانات ثانوية أقل بروزًا مع بقاء التباين، ومسافات متسقة | المرشح + الوظيفة ← المطلوب ← الموعد والمسؤول ← زر التنفيذ |
| الأيقونات السريعة | أيقونة موحدة لكل نوع نشاط ومصحوبة بتسمية واضحة | هاتف للمكالمة، تقويم للمقابلة، قائمة للتقييم، مستند للمرفقات، ساعة للانتظار |
| استخدام الهوية | الحفاظ على SGH والأزرق/الأخضر والخط والـtokens الموجودة؛ تقليل التشابه بين العناصر القابلة للضغط والمعلومات الثابتة | زر أساسي مميز، وعناصر ثانوية واضحة بدون منافسته |
| الشاشات الصغيرة | الحفاظ على الإجراء الأساسي والمعنى قبل التفاصيل، واحتواء التمرير داخل اللوحة عند الحاجة | ترتيب البطاقة عموديًا وتثبيت اسم الإجراء، دون تجاوز عرض المستند |
| Light / Dark | نفس دلالات الحالة في الوضعين مع فحص الأيقونة والنص والخلفية وأثر التركيز | تنبيه متأخر واضح في الوضعين دون الاكتفاء بخلفية حمراء |

تظهر المراجعة البصرية السابقة بطاقات وأزرار متشابهة وخطوطًا ثانوية صغيرة في مواضع؛ لم نقس نسب التباين أو نختبر Dark لهذه الإضافة، لذلك لا يوجد حكم بوجود مخالفة تباين محددة ولا شهادة وصول. قبل اعتماد التنفيذ تقاس نسب النصوص والأزرار والتركيز في الحالتين، ويُختبر الكيبورد والتسميات واللمس.

### قاموس الأيقونات المقترح

| المعنى | الأيقونة مع النص | المكان الذي تفتح منه |
| --- | --- | --- |
| مكالمة | Phone + «اتصل / سجّل مكالمة» | مهمة اليوم وملف المرشح |
| متابعة | Clock + «متابعة» مع موعد وحالة | My Work والملف، مع إكمال/إعادة جدولة |
| مقابلة | Calendar + «جدولة / تفاصيل المقابلة» | بطاقة المرشح والملف والمقابلات |
| تقييم | ClipboardCheck + «التقييم» مع المكتمل/المطلوب | المقابلة والملف، حسب دور المستخدم |
| مستندات | FileText + «المستندات» مع العدد عند توفره | ملف المرشح/التقديم |
| عرض | FileSignature + «العرض» مع حالته | الملف وMy Work حسب الصلاحيات |
| متوقف | TriangleAlert + سبب مقروء | بطاقة الـPipeline والملف |
| الخطوة التالية | ArrowRight + فعل محدد | الصف أو بطاقة المرشح، مع عدم عرض زر بلا وجهة |

الأعداد في أزرار المقابلات أو المستندات تظهر فقط من بيانات تم تحميلها بنجاح؛ فشل التحميل ليس صفرًا. على الهاتف يحافظ الزر على اسم واضح ومساحة لمس مناسبة. الأزرار التي يقتصر شكلها على أيقونة تحتاج اسمًا قابلًا للقراءة المساعدة وتركيزًا واضحًا.

## تصور الشاشات الأربع

1. **My Work:** مقدمة قصيرة، فلاتر واضحة للتأخر واليوم والانتظار، ثم صفوف فيها أيقونة نوع العمل واسم المرشح/الوظيفة والموعد والمسؤول وزر الخطوة. المقابلات القادمة والانضمام قسما وصول واضحان؛ الملخص لا يعرض عدادًا بتعريف مختلف عن القائمة.
2. **Open jobs:** الحفاظ على القائمة التفصيلية، مع عنوان ومالك وفرع وشواغر وحالة، وعدد يحتاج فعلًا عند توفره. ضغطة الوظيفة تفتح لوحة مراحلها، مع تمييز وظائف الفريق المقيدة بالنص والأيقونة.
3. **Pipeline:** لكل بطاقة مرشح: الاسم، الخطوة، تنبيه التعطيل أو موعد المتابعة، وفعل واحد مناسب للمرحلة. تجمع الأفعال الأقل تكرارًا في قائمة واضحة، مع بديل لتحريك المراحل بالكيبورد.
4. **ملف التقديم:** رأس صغير يبين الشخص والوظيفة والمرحلة والمالك؛ إجراء أساسي يتغير بالمرحلة؛ اختصارات مكالمة ومتابعة ومقابلة ومستندات حسب الصلاحية؛ نشاط زمني مفصول عن سجل النظام. الرجوع يحافظ على الشاشة والفلتر.

هذه تصورات تنفيذ، وليست إقرارًا بأن كل اختصار أو عدد يعمل حاليًا. القيم الوهمية ونسب الملاءمة غير المبررة في أي صورة مرجعية لا تُنقل للتطبيق. الواجهات تحترم بيانات الرواتب والصلاحيات الحالية، ولا تُحوّل الاقتراحات إلى قرارات توظيف آلية.

## التحقق المطلوب عند التنفيذ

- اختبار من My Work → إجراء → حفظ أو خطأ → رجوع للقائمة نفسها، مع المهمة غير المرتبطة والمرشح ذي أكثر من تقديم.
- فحص الألوان والنصوص وحالات الأزرار والتركيز في Light وDark، وبالكيبورد، وعند 375 و768 و1024 و1440px؛ بما فيها الشريط المتجاوز في ملف التقديم.
- اختبار حالات تحميل جزئي، خطأ، عدم وجود نشاط، دور بلا صلاحية، وإعادة المحاولة أو التعارض؛ لا تُعرض بيانات فاشلة كقوائم فارغة.
- مراجعة المقابلة والتقييم والعرض والمستندات والتعيين النهائي ببيانات اختبار محلية؛ إثبات الحفظ وربط الحالات عبر الشاشات قبل اعتبارها مكتملة.

لم تُجر هذه الإضافة تعديلات في التطبيق أو اختبارات حفظ. المراجع المرئية هي ملفات المشروع واللقطات التي فُحصت في جولة التدقيق السابقة؛ المقارنة الخارجية من وثائق Odoo الرسمية، ولم يتم تشغيل حساب Odoo مباشر.
